# Accelerator matrix and VLM oracle, 2026-08-29

Corpus: an 11-page two-column paper (`Diffusion_models_are_continuous_human_noise_operators.pdf`)
and two Gmail-printed receipts (3 pages, 1 page). Oracle: Cohere Labs North Micro Vision Instruct
(2.4B, Apache 2.0, the open base of Cohere's Parse 5), served by
`grpc-vlm-convert/serving/north-micro-vision/` on transformers 5.16.1 with greedy decoding.
Hardware: RTX 4080 SUPER (16 GB), Intel Arc Pro B70 on krick-1, 16 cores of a Ryzen 9 9950X.

## The VLM on three accelerators (`cuda`, `xpu`, `cpu` legs)

| leg | paper (11 p) | receipt (3 p) | receipt (1 p) | output vs CUDA |
|---|---|---|---|---|
| RTX 4080 SUPER | 128 s, 79 tok/s | 14.3 s, 61 tok/s | 2.4 s, 86 tok/s | reference |
| Arc Pro B70 (xpu) | 175 s, 58 tok/s | 14.7 s, 60 tok/s | 3.6 s, 57 tok/s | a few lines differ (bf16 numerics); 1-page receipt identical |
| CPU, 16 cores | 1412 s, 7.3 tok/s | 139 s, 6.3 tok/s | 35.6 s, 5.8 tok/s | 1-page receipt identical; long pages diverge (no HTML tables on the paper) |

Agreement of the VLM with gRParse's default route (inspector fast path) on the paper: letter
similarity 0.95, word recall 0.95, precision 0.91. The receipts score lower for two known reasons:
gRParse keeps page furniture (Gmail's date line, the print URL) out of the body markdown while the
VLM transcribes it, and the VLM transcribes link anchor text where gRParse also carries the href.

## gRParse's own CV path on three accelerators (`grparse-*` legs, `COLLECTOR_GRPARSE_CV` forced)

Scored against the saved CUDA oracle output, so only gRParse changes between rows.

| leg | paper cold | paper warm | receipt 3 p | receipt 1 p | output |
|---|---|---|---|---|---|
| CUDA (RTX 4080 SUPER) | 1.57 s | 0.28 s | 0.06 s | 0.02 s | reference |
| OpenVINO GPU (Arc Pro B70) | 7.99 s (kernel compile) | 0.83 s | 0.25 s | 0.09 s | byte-identical to CUDA |
| CPU, heron layout | 4.51 s | 4.66 s | 1.38 s | 0.26 s | byte-identical to CUDA |
| CPU, picodet layout (the image's old default) | 2.06 s | 2.07 s | 0.48 s | 0.05 s | different: the 1-page receipt came out one word per paragraph |

Finding: the published CPU image pinned `GRPARSE_LAYOUT_MODEL=picodet` for speed, and its output
was never compared with the GPU images on real pages. With `heron` every image produces the same
document; the CPU image now defaults to it (`Dockerfile.cpu`), and `picodet` remains the explicit
speed flip.

The parse-stack CUDA container (page previews on, cores shared with the CPU VLM run at the time)
measured 2.95 s on the paper; the standalone rows above are the like-for-like numbers.

## Reproduce

```sh
# serve the oracle (one of): serving/north-micro-vision/compose.yaml --profile cuda|xpu|cpu
# gRParse legs: compose.stack.yaml (CUDA), compose.stack.openvino.yaml, compose.stack.cpu.yaml,
#               with compose.stack.expose-grpc.yaml to publish 50051
EVAL_LABEL=cuda GRPARSE_TARGET=localhost:50051 VLM_ENDPOINT=http://localhost:8086 \
  EVAL_CORPUS=/path/to/pdfs uv run --with grpcio --with grpcio-tools python eval/compare_vlm.py
EVAL_LABEL=grparse-openvino GRPARSE_TARGET=krick-1:50051 GRPARSE_COLLECTORS=COLLECTOR_GRPARSE_CV \
  VLM_ENDPOINT=http://localhost:8086 VLM_REFERENCE=eval/out/cuda EVAL_CORPUS=/path/to/pdfs \
  uv run --with grpcio --with grpcio-tools python eval/compare_vlm.py
python eval/summarize.py eval/out
```
